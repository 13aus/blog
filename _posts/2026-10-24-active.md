## TL;DR

After scanning the machine and discovering anonymous access to the `Replication` share, a username and password were found in the `Groups.xml` file. The password was stored in the `cpassword` attribute and could be decrypted using the `gpp-decrypt` tool.

With the recovered credentials, LDAP enumeration was performed, revealing an Administrator account with an associated Service Principal Name (SPN). This account was vulnerable to Kerberoasting, allowing a Kerberos service ticket to be requested and extracted. A portion of the ticket is encrypted using a key derived from the Administrator account's password, making it possible to perform an offline password-cracking attack.

After successfully recovering the Administrator account's plaintext password, Impacket's `wmiexec` or `psexec` could be used to establish a remote shell session with elevated privileges.

## Recon

### Nmap
I started with the following nmap command to get an idea of what services are available on the target.

```bash
nmap -sT 10.129.75.74 -p- -Pn --disable-arp-ping -n -vv --reason --stats-every 8s
```
- The command break down:
	- `-sT` - A standard TCP scan.
	- `-p-` - All ports.
	- `-Pn` - No ping host discovery. (I know the host is up, so there is no reason for the tool to generate more traffic than needed.)
	- `--disable-arp-ping` - More optimization. Can disregard the arp, if any happens, and assume the host is up.
	- `-n` - No hostname resolution.
	- `-vv` - very verbose. (Detailed output.)
	- `--reason` - The reason why the port is in the state that it is in.  The response, or lack of response from the port.
	- `--stats-every 8s` - Stats every 8 seconds.

![nmap scan]({{ '/assets/img/active/ActiveNmapScan.png' | relative_url }})

SMB can sometimes contain valid credentials, so I started there.

### SMB Enumeration (Port 445)
`smbclient` was able to list the available shares using the null session option.
```bash
smbclient -L \\\\10.129.75.74\\ -N
```
![nmap scan]({{ '/assets/img/active/SMBclientShareListing.png' | relative_url }})

The `Replication` share was accessible through a null session, so I proceeded to enumerate the share.  It didn't have much information but the `\active.htb\Policies\{31B2F340-016D-11D2-945F-00C04FB984F9}\MACHINE\Preferences\Groups\` path housed the `Groups.xml` file.

![nmap scan]({{ '/assets/img/active/GroupsXMLFind.png' | relative_url }})

`Groups.xml` is a file associated with Group Policy Preferences (GPP). It is commonly found in older Windows Server environments, such as Windows Server 2008, and was designed to simplify administrative tasks across a domain. These tasks include mapping network drives, creating scheduled tasks, and configuring registry values.

In some cases, Group Policy Preferences can also be used to update local account passwords or create and deploy local accounts across multiple hosts. To perform password-related operations, the configuration may contain account credentials. Historically, these passwords were stored in an encrypted format using a static AES encryption key published by Microsoft.

The encrypted passwords are stored in the `cpassword` attribute within the XML file. Unfortunately, because Microsoft publicly documented the encryption key in MSDN, anyone with access to the encrypted value can decrypt it and recover the original password.

![nmap scan]({{ '/assets/img/active/CPasswordFoundinFile.png' | relative_url }})

`gpp-decrypt` can be used to decrypt the password, which returns the plaintext `GPPstillStandingStrong2k18`.  
```bash
gpp-decrypt "edBSHOwhZLTjt/QS9FeIcJ83mjWA98gw9guKOhJOdcqh+ZGMeXOsQbCpZ3xUjTLfCuNH8pG5aSVYdYw/NglVmQ"
```
![nmap scan]({{ '/assets/img/active/CrackingGPPPassword.png' | relative_url }})

The recovered credentials can be used to authenticate to the LDAP service and enumerate domain users.

## LDAP (Port 636) Enumeration
`ldapsearch` is used, along with the credentials, to extract information about domain users.

```bash
ldapsearch -x -H ldap://10.129.74.54 -D 'SVC_TGS' -w 'GPPstillStandingStrong2k18' -b "DC=active,DC=htb" "(objectclass=user)"
```
![nmap scan]({{ '/assets/img/active/LDAPSearchResults.png' | relative_url }})
The `Administrator` account is found with a Service Principal Name(SPN), which means that a service is running with the Administrator account.

## Foothold
Using the previously recovered credentials, `Impacket-GetUserSPNs` can request a Kerberos service ticket (TGS) for the Administrator account. A portion of the ticket is encrypted using a key derived from the account's password, allowing for offline password cracking.

```bash
impacket-GetUserSPNs active.htb/SVC_TGS:'GPPstillStandingStrong2k18' -dc-ip 10.129.75.74 -request
```

![nmap scan]({{ '/assets/img/active/KerberoastingHash.png' | relative_url }})

The password hash can be copied into a file and then cracked with `hashcat` and the `rockyou.txt` wordlist.
```bash
./hashcat -a 0 -m 13100 ../hash/test.hash ../lists/rockyou.txt
```
![nmap scan]({{ '/assets/img/active/HashcatSuccess.png' | relative_url }})

With the Administrator account's password recovered, Impacket's `wmiexec` or `psexec` can be used to establish a remote shell with elevated privileges.
```bash
impacket-wmiexec administrator:Ticketmaster1968@10.129.75.74
```
![nmap scan]({{ '/assets/img/active/RootAccess.png' | relative_url }})

## Takeaway
There was quite a few things that I didn't know with this one, which prompted me to do a bit of a deeper dive on the concepts.  I like to understand why things happen, so here I hope to impart what I have learned.

I did not know about the encrypted password that was stored in the `Group.xml` file relating to Group Policy Preferences.  Storing passwords in the clear is a bad idea, and Microsoft's solution to this was to encrypt the password in the file.  However, the AES key that could reverse that encryption was published in their documentation making the encryption moot.  Microsoft's response to this event was to deploy a patch, which disable the feature altogether on Windows Server 2008.  It's good to keep in the back of the mind when testing Windows Server 2008, because the patch did not remove `Group.xml` files that were created before the patch update.

Also, I decided to do a deeper dive into Service Principal Names(SPNs) and Kerberoasting.  Service Principal Names act as a way for the domain to identify services running as a specific user.  Typically, a domain should utilize accounts with limited privileges for provided services.  Any authenticated user can request a ticket for a service, and when the ticket is returned by the KDC it is encrypted with the service account's password hash.  Extracted password hashes can then be taken offline to crack.  

Passwords should be long and complicated to help prevent an account take over like this.  An attacker is not using a special tool to get the ticket, but abusing the normal functionality of the domain.

Lastly, I took a look at Impacket's `wmiexec` and `psexec`.  Both function over SMB(port 445), and act as a way for admins to copy files or administer patches remotely.  Windows servers are shipped with remote-management channels turned on, and automatically expose hidden shares only accessible by an admin.  `PSEXEC` authenticates to SMB, drops a service binary, and then starts the binary with `SYSTEM` level privileges.  That means that the `psexec` tool can actually escalate privileges, but comes at the cost of creating extra noise on the wire.  `WMIEXEC` is different as it uses the Windows Management Instrumentation to create a process and then return the feedback of that process to standard output.  The only caveat to connecting with `wmiexec` is that you will be running commands as the authenticating user.

Both are great ways to get shell access to a machine that otherwise does not have standard remote management ports open.
